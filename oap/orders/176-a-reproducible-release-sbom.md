# OAP Work Order — 176-a

PR mode: `CREATE_NEW_PR`

## Objective

Resolve the stale-SBOM release-hygiene debt: replace the RC1-era
point-in-time developer-venv snapshot at `sbom/cyclonedx.json` with a
scoped, reproducible release SBOM generated by a documented
stdlib-only script from an exact frozen production-dependency
resolution, plus a CI static validation step. No runtime, dependency,
or build-input change of any kind.

## Strategic rationale (machine-verified 2026-09-20)

The maintainer's release direction (2026-09-20) requires: "Resolve the
stale SBOM situation before final release/tagging." The strategic model
machine-verified on 2026-09-20 that the current artifact is
unusable as a release SBOM:

- `sbom/cyclonedx.json` is a flat 88-component CycloneDX 1.5 snapshot
  of a one-off developer virtualenv (production PLUS dev/test tools:
  `pytest`, `pytest-asyncio`, `pytest-xdist`, `playwright`,
  `hypothesis`, `testcontainers`, `docker`, `respx`, and even
  `pip`/`setuptools`/`wheel`), with duplicate
  `slaif-api-gateway @ 0.1.0` entries, `metadata.component`
  `slaif-api-gateway 0.1.0rc1` (RC1 era), `metadata.tools` absent
  (generation method not recorded), `dependencies` empty (no graph),
  and versions stale against current pins (`openai 2.41.0` vs
  `3.14.1`, `gunicorn 26.0.0` vs `26.2.0`, `pydantic 2.13.4` vs
  `2.13.5`, `ruff 0.15.16` vs `0.16.7`).
- The Objective-173 dated record classified it as a "point-in-time
  snapshot ... stale w.r.t. the 166/171/172 dev pins ... regeneration
  remains a release-time decision of the human maintainer"; the
  maintainer has now made that decision: resolve it before tagging.
- `docs/supply-chain.md` itself instructs: "Regenerate and review the
  SBOM ... for the exact release candidate before a release decision."
- Reproducibility investigation: `pyproject.toml` production
  dependencies (21 direct) are UNPINNED; the `Dockerfile` runs
  `pip install --upgrade pip && pip install .` (live resolution at
  image build time); CI installs `.[dev]` live;
  `requirements.txt`/`requirements-dev.txt` are unpinned mirrors not
  referenced by any build or CI step; no lock file exists. Therefore
  the release SBOM must be an explicitly scoped, point-in-time FROZEN
  record of the production dependency graph, generated by a documented
  mechanism — and the live-resolution limitation must be documented,
  not hidden. Pinning the 21 direct production dependencies would
  change `pyproject.toml` (a Docker build input) and thus the
  qualified runtime/deployment identity — that is a
  runtime-identity-changing hardening, deliberately post-RC, and is
  EXCLUDED from this objective.

Design decision (strategic, recorded here): the SBOM is generated by a
stdlib-only script in two stages — (1) freeze: an ephemeral venv
installs exactly the 21 direct production dependencies parsed from
`pyproject.toml` (tomllib; nothing hardcoded) and `pip freeze`
captures the exact transitive production graph; (2) emit: deterministic
CycloneDX 1.5 JSON from that freeze, with recorded generator tools,
exact `metadata.component`, and timestamp. A stdlib-only structural
validator runs in CI. This is the smallest mechanism that yields a
documented, valid, scoped, CI-guarded release SBOM with the repository's
actual tooling (pip + Python 3.12 stdlib); container-image scanning
(syft-class) is the gold standard but requires new tooling not present
in the repository and is out of scope for release hygiene.

## Required change (exact)

Five functional paths:

1. `scripts/generate_sbom.py` (NEW, stdlib only, Python >= 3.12,
   executable via `python scripts/generate_sbom.py`):
   - Stage 1 (freeze): create an ephemeral venv in a fresh temporary
     directory (`python -m venv --clear <tmpdir>`), then install
     EXACTLY the direct production dependencies parsed from
     `[project] dependencies` in `pyproject.toml` via `tomllib`
     (never hardcoded), then capture `pip freeze`. Remove the venv
     bootstrap dists `pip`, `setuptools`, `wheel` from the freeze and
     document that removal. On resolution failure, exit non-zero with
     the pip error output (never force with `--no-deps` or similar).
   - Stage 2 (emit): write `sbom/cyclonedx.json` deterministically
     from the freeze: `bomFormat: "CycloneDX"`,
     `specVersion: "1.5"`, `version: 1`; `metadata.timestamp` =
     generation time (ISO 8601); `metadata.component` =
     `{name: "slaif-api-gateway", version: <version parsed from
     pyproject [project] version>, type: "application"}`;
     `metadata.tools.components` recording the generator
     (`{type: "application", name: "slaif-generate-sbom",
     version: "1.0"}` plus `{type: "library", name: "Python",
     version: <interpreter version>}`); `components` = one
     `{type: "library", name, version, purl: "pkg:pypi/
     <normalized-name>@<version>"}` entry per freeze line, sorted by
     normalized name; no `serialNumber`; no `dependencies` graph
     (document: flat component list, CycloneDX 1.5). The script
     prints the component count and the exact freeze source line
     count, and exits non-zero if any freeze entry lacks a version.
2. `scripts/check_sbom.py` (NEW, stdlib only): load
   `sbom/cyclonedx.json` and assert — `bomFormat == "CycloneDX"`,
   `specVersion == "1.5"`, `metadata.component.name ==
   "slaif-api-gateway"`, `metadata.component.type ==
   "application"`, non-empty `metadata.component.version`,
   non-empty `metadata.tools.components`, parseable ISO 8601
   `metadata.timestamp`, non-empty `components` where every entry has
   `type`/`name`/`version`/`purl` with `purl` starting
   `pkg:pypi/`, no duplicate component names, and NO occurrence of
   any dev/test/bootstrap package name from the exact list: `pip`,
   `setuptools`, `wheel`, `pytest`, `pytest-asyncio`, `pytest-xdist`,
   `playwright`, `hypothesis`, `ruff`, `testcontainers`, `respx`,
   `openai` (the last two are dev/test-only per pyproject
   `[project.optional-dependencies] dev`). On success print exactly
   `SBOM_CHECK=OK components=<n>` and exit 0; otherwise print the
   failing assertions and exit non-zero.
3. `sbom/cyclonedx.json` (REGENERATED): produced by running
   `python scripts/generate_sbom.py` on the final tree; the committed
   artifact is the script's output.
4. `docs/supply-chain.md` (REWRITTEN): keep the existing honest
   non-attestation stance, and state exactly: the SBOM scope (production
   runtime dependencies only; dev/test tooling explicitly excluded);
   the generation mechanism (exact command `python scripts/generate_sbom.py`,
   stdlib only, Python >= 3.12, two-stage freeze+emit as implemented);
   what it attests (a point-in-time frozen production dependency graph
   for the release candidate; valid CycloneDX 1.5; structurally
   validated in CI by `scripts/check_sbom.py` in the `Unit, lint, and
   migration head` job); what it does NOT attest (not signed provenance,
   not a vulnerability scan/advisory review, not an attestation of
   build-time resolution — the Dockerfile live-resolves the unpinned
   direct production dependencies at image build time, a documented
   limitation; regeneration produces a new timestamp and may yield
   different versions until the direct production dependencies are
   pinned, which is deliberately post-RC); the regeneration procedure;
   and the status of `requirements.txt`/`requirements-dev.txt`
   (unpinned mirrors not referenced by any build or CI step; not a
   build input). Do not remove the existing statements that CI does
   not run pip-audit/Safety, does not sign images, and does not
   publish attestations.
5. `.github/workflows/ci.yml` (ONE step added): in the `unit-lint`
   job (check name `Unit, lint, and migration head`, unchanged), add
   exactly one step after `Install package with development
   dependencies`: `- name: Check SBOM validity` / `run: python
   scripts/check_sbom.py`. No other workflow line changes; no check
   name changes.
