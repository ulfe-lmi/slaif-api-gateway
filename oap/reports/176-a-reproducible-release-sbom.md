### `docs/supply-chain.md` (verbatim rewritten document; AP-4)

```markdown
# Supply-chain evidence

> **Status:** Bounded repository evidence; not signed provenance or vulnerability certification
> **Audience:** Maintainers and security reviewers

The repository contains a CycloneDX SBOM at `sbom/cyclonedx.json`, Dependabot
configuration, CodeQL analysis, pinned versions for selected development tools,
and standard GitHub dependency metadata. The application is Apache-2.0 licensed.

Current CI does **not** run pip-audit or Safety, does not sign container images,
does not publish attestations, and does not prove that no high-severity advisory
exists. Regenerate and review the SBOM and dependency advisories for the exact
release candidate before a release decision.

Do not describe the current artifacts as signed provenance, a complete license
audit, an accepted vulnerability-risk register, or supply-chain certification.

## Release SBOM scope and generation mechanism

The release SBOM at `sbom/cyclonedx.json` is a scoped, point-in-time record of
the **production runtime dependencies only**. Development and test tooling
(`pytest`, `pytest-asyncio`, `pytest-xdist`, `playwright`, `hypothesis`,
`testcontainers`, `respx`, `openai`, and the venv bootstrap dists `pip`,
`setuptools`, `wheel`) is explicitly excluded from the scope.

The SBOM is generated by the stdlib-only script `scripts/generate_sbom.py`
(Python >= 3.12) with the exact command:

    python scripts/generate_sbom.py

The script runs in two stages:

1. **Freeze.** It creates an ephemeral virtualenv in a fresh temporary
   directory, installs exactly the direct production dependencies parsed from
   `[project] dependencies` in `pyproject.toml` via `tomllib` (nothing is
   hardcoded), and captures `pip freeze` as the exact frozen transitive
   production graph. The venv bootstrap dists `pip`, `setuptools`, and `wheel`
   are removed from the freeze because they are virtualenv tooling, not project
   dependencies. On pip resolution failure the script prints the pip output
   and exits non-zero; it never forces resolution with `--no-deps` or similar.
2. **Emit.** It writes `sbom/cyclonedx.json` deterministically from the freeze
   as a flat CycloneDX 1.5 component list: `bomFormat` `CycloneDX`,
   `specVersion` `1.5`, `version` `1`, the generation time in
   `metadata.timestamp`, the exact `metadata.component`
   (`slaif-api-gateway`, version parsed from `pyproject.toml`, type
   `application`), the generator recorded in `metadata.tools.components`
   (`slaif-generate-sbom` plus the Python interpreter version), and one
   `library` component with a `pkg:pypi/` purl per freeze line, sorted by
   normalized name. The document carries no `serialNumber` and no
   `dependencies` graph.

The committed artifact is the script's own output on the current tree. The
only network interaction during generation is ordinary PyPI package
resolution during stage 1.

## What the SBOM attests

- A point-in-time frozen production dependency graph for the release
  candidate: the exact package names and versions resolved when the SBOM was
  generated.
- A valid CycloneDX 1.5 document.
- Structural validity in CI: `scripts/check_sbom.py` runs in the
  `Unit, lint, and migration head` job of `.github/workflows/ci.yml` and
  fails the build if the SBOM is missing, malformed, or contains an excluded
  dev/test/bootstrap package.

## What the SBOM does not attest

- It is **not signed provenance**: no signature, SLSA attestation, or
  build-reproducibility claim accompanies it.
- It is **not a vulnerability scan or advisory review**: CI does not run
  pip-audit or Safety, and the SBOM carries no vulnerability data.
- It is **not an attestation of build-time resolution**: the `Dockerfile`
  live-resolves the unpinned direct production dependencies at image build
  time, so an image built later may resolve different versions than the
  frozen record. Regeneration produces a new timestamp and may yield
  different versions until the direct production dependencies are pinned,
  which is deliberately post-RC.

## Regeneration procedure

To regenerate the release SBOM on the exact release candidate, run:

    python scripts/generate_sbom.py

The script rewrites `sbom/cyclonedx.json`; commit the regenerated artifact
together with the release. Validate it locally with:

    python scripts/check_sbom.py

which prints `SBOM_CHECK=OK components=<n>` on success.

## requirements files

`requirements.txt` and `requirements-dev.txt` are unpinned mirrors of the
`pyproject.toml` dependency lists. They are not referenced by any build or CI
step and are not a build input.
```
