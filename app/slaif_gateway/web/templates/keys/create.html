One key can carry one Chat client (OpenCode Chat or Hermes) and one Responses client (Codex or OpenCode Responses) together; conflicting pairs are refused with an explanation. The gateway applies the matching reviewed client profile and rechecks the routes before the key is created.

What is this for?

In plain terms, each choice opens one client wire on this key:

  • Codex: the Codex agent client for the Qwen models. You still choose the explicit Qwen models and their providers above; the endpoints /v1/models and /v1/responses are preselected for you.
  • OpenCode (Chat): OpenCode talking over Chat Completions. The /v1/chat/completions endpoint is preselected for you.
  • OpenCode (Responses): OpenCode's tool loop over the Responses endpoint. It needs explicit models/providers and routes that already carry the OpenCode Responses gates; the /v1/responses endpoint is preselected for you.
  • Hermes (Chat): Hermes over Chat Completions only. Hermes is never a Responses client, so this choice never implies Responses access.

Choosing a client installs nothing and touches no provider. It does not widen any allow list: if the routes cannot serve a choice, the create is refused and the page says exactly which model/provider route is missing and where to fix it.

Hard Quota Limits

Inactive in document mode: the configuration document defines these limits. The guided inputs are submitted at their blank (unlimited) defaults.

These are the key's lifetime ceilings: the most it may spend, use, and call across its whole validity. Leave a field blank for no ceiling on that measure.

Maximum spending recorded for this key over its lifetime, in EUR. Leave blank for no total spending limit. Use a finite amount for a trial or workshop; a request already running can still exceed the remaining amount. This is not an exact provider-invoice cap.

Maximum total text-processing usage over the key's lifetime, including inputs and outputs. Leave blank for no total token limit. Enter a whole token count; for example 1000000 is one million tokens.

Maximum number of requests counted against the key's lifetime quota. Leave blank for no total request limit. For example, 100 allows a small trial. Whether a failed attempt counts depends on where it fails.

Technical details

These limits are backed by the gateway's hard quota accounting (PostgreSQL), and they are separate from the speed controls further down this page: a key can exhaust its lifetime budget even while every single request is admitted. Blank means UNLIMITED for that lifetime quota (stored null, never zero); in a configuration document the same null/omission law applies. Example: with a 500 EUR cost limit, the gateway stops admitting NEW requests once the used cost approaches 500 EUR; a request that already started may finish, so the final provider bill can slightly exceed the limit.

When a rate limit is reached

Optional lazy (waiting) throttling for this key. Waiting precedes provider execution; queue full or deadline returns 429, and disconnected requests are canceled. Hard quota, security, and hosted-tool fence refusals remain immediate, and streaming starts only after admission.

Reject returns a rate-limit error immediately; wait briefly queues a request until capacity is available. Keep reject for ordinary batch use; waiting can make interactive clients smoother. Full queues, expired waits, and hard budget or security refusals still return an error.
