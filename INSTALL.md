# Installation

> **Status:** Canonical installation overview
> **Short boot:** The [quickstart](QUICKSTART.md) is the one-sitting,
> provider-free path; this page covers prerequisites, persistence, the
> production topology, upgrades, and stop/cleanup semantics.

## Prerequisites

Verified against the repository's Compose packaging:

- **Linux** host (this installation is documented and tested for Linux; we do
  not claim macOS or Windows support).
- **Docker** with **Compose v2**.
- **Git**, to clone the repository.
- Free local ports for the development stack: API `8000`, PostgreSQL `15432`,
  Redis `16379`, Mailpit SMTP `1025`, Mailpit web `8025` (all configurable via
  `*_HOST_PORT` settings in `.env`). The production topology binds `80`/`443`
  through Nginx plus a host-loopback API diagnostic port (`127.0.0.1:8000` by
  default).

No host Python installation is required to run the Gateway; everything runs
in containers. Host Python is only needed for local development and testing
(see [CONTRIBUTING.md](CONTRIBUTING.md)).

## Local installation (development and evaluation)

The canonical step-by-step sequence — clone, copy the config template,
generate the three runtime secrets, build, start PostgreSQL/Redis/Mailpit, run
migrations explicitly, start the API, check health/readiness, create the
first admin, and log in — is the [quickstart](QUICKSTART.md#milestone-1-provider-free-boot).
The points below are the invariants to keep in mind:

- **Config.** `.env.example` is a curated local template, not an exhaustive
  catalog of settings. Copy it to `.env` (never commit `.env`; restrict it
  with `chmod 600` on shared systems) and read the
  [configuration reference](docs/configuration.md) for every supported
  setting, default, and production override.
- **Secrets.** The three runtime secrets (`TOKEN_HMAC_SECRET_V1`,
  `ADMIN_SESSION_SECRET`, `ONE_TIME_SECRET_ENCRYPTION_KEY`) are generated by
  `slaif-gateway secrets generate ... --write` through the Docker-only
  bind-mounted workflow in the quickstart. `--write` is a clear-text local
  bootstrap convenience, not a production secret-management system.
- **Migrations are explicit.** `slaif-gateway db upgrade` is the only
  migration path; API, worker, and scheduler never migrate on startup.
- **Start/health.** `docker compose up -d postgres redis mailpit`, migrate,
  then `docker compose up -d api worker scheduler`; verify
  `http://localhost:8000/healthz` and `/readyz`.

### Persistence

Development Compose stores data in the named volumes `postgres-data` and
`redis-data`. `docker compose down` stops containers but preserves both
volumes; `docker compose down -v` **deletes them** (see Stop and clean up
below). PostgreSQL is the source of truth for keys, quotas, accounting,
audit, and admin state; plaintext gateway keys are never stored, so a
database backup alone does not restore key material — protect the HMAC and
one-time-secret key versions separately (see
[backup and restore](docs/backup-restore.md)).

### Local refresh

After `.env` changes or code updates, the bundled helper
`./scripts/docker-refresh.sh` (`--env-only`, `--pull`, or full) rebuilds and
recreates the runtime services non-destructively: it never deletes volumes,
overwrites `.env`, or resets git state. It is a local convenience, not a
production upgrade tool.

## Production-style installation

The production appliance is a separate Compose project
(`docker-compose.production.yml`) with a different secret and network model.
The detailed procedure, including secret-file creation and the preflight
check, is [deployment-production.md](docs/deployment-production.md). The
topology:

- **postgres** — PostgreSQL 16, authenticated by a file-backed secret, named
  volume, private network only.
- **redis** — Redis 7 with authentication and protected mode from
  file-backed secrets; no published port.
- **migrations** — a one-shot service that runs `alembic upgrade head` and
  must complete successfully before the API starts.
- **api** — the Gateway on private networks with egress; the only host
  binding is the loopback diagnostic port
  `127.0.0.1:${SLAIF_API_DIAGNOSTIC_PORT:-8000}`.
- **nginx** — the public HTTPS boundary on `80`/`443` with your TLS
  certificates; starts only after the API reports healthy.
- **worker / scheduler** — optional `async` profile for email delivery and
  scheduled jobs; without it, reconciliation remains available through the
  CLI.

Production rules that differ from the local workflow:

- **File-backed secrets.** Every secret is a file under `secrets/`
  (directory mode `0700`). The image entrypoint
  (`deploy/production/load-secrets.sh`) loads the allowlisted `*_FILE`
  variables and rejects direct production secret environment variables,
  symlinks, empty files, and NUL bytes.
- **Nonempty provider secrets.** Enabled providers require non-placeholder
  provider key files in production; the local provider-free promise does not
  apply to production.
- **Explicit migrations.** Because migrations run as a one-shot service,
  applying migrations after an image refresh means recreating that service
  (for example with `docker compose -f docker-compose.production.yml up -d
  --force-recreate migrations`, waiting for successful completion, then
  recreating the API). Follow the
  [upgrade runbook](docs/upgrade-runbook.md) for the full controlled-upgrade
  procedure, including backup/restore rehearsal.

Run the fail-closed preflight before deploying:

```bash
bash scripts/preflight.sh
```

It verifies secret files, directory mode, TLS files, Docker availability,
and Compose configuration.

## Interface exposure

- Local: the API is reachable at `http://localhost:8000` (`/v1`,
  `/admin`, `/healthz`); `/readyz` and `/metrics` are internal/allowlisted.
- Production: only Nginx ports `80`/`443` are publicly bound; `/metrics` is
  not published by the production Nginx configuration, and `/readyz` is
  allowlisted to private networks by default.

## Stop and clean up

- **Non-destructive stop (local):** `docker compose down` — containers stop;
  the named data volumes survive.
- **Non-destructive stop (production):**
  `docker compose -f docker-compose.production.yml down` — same semantics for
  the production project.
- **Destructive (use conspicuously):** `docker compose down -v` (or the
  production equivalent) deletes the project's data volumes. For SLAIF this
  deletes the PostgreSQL source of truth — keys, quotas, usage ledger, audit
  logs, and admin state. Plaintext keys are unrecoverable by design; back up
  PostgreSQL and protect secret key versions before any destructive cleanup
  (see [backup and restore](docs/backup-restore.md)).
